# Auto-CoT 논문 분석 (Zhang et al., 2022)

> *Automatic Chain of Thought Prompting in Large Language Models* — Zhuosheng Zhang, Aston Zhang, Mu Li, Alex Smola (SJTU / AWS), arXiv:2210.03493

이 논문은 CoT 원론 논문이 아니라 **Auto-CoT**(few-shot 예시를 자동 생성하는 방법)를 다룬다. 평가 과제는 산술·상식·기호 추론이며, 텍스트 분류나 영업 메모 같은 비정형 데이터는 직접 다루지 않는다.
아래에서 **[논문]**은 논문 내용, **[추론]**은 실무에 맞춘 확장이다.

## 1. 핵심 요약

**문제와 방법**
- Manual-CoT는 성능이 좋지만 예시를 사람이 하나씩 설계해야 하고, 작성자에 따라 정확도가 최대 28.2%p 차이 난다.
- Zero-Shot-CoT("Let's think step by step")로 예시를 자동 생성하면 추론 오류가 섞이고, 유사 질문 검색 방식은 같은 오류를 반복시킨다("misleading by similarity").
- 그래서 질문을 Sentence-BERT + k-means로 군집화하고, 군집마다 중심에 가까운 질문 하나를 골라 Zero-Shot-CoT로 추론 체인을 만든 뒤(질문 60토큰 이하, 추론 5단계 이하) few-shot 예시로 쓴다.

**Zero-shot / Few-shot 대비 성능** (Table 3, GPT-3 text-davinci-002)

| | MultiArith | GSM8K | CSQA | StrategyQA |
|---|---|---|---|---|
| Zero-Shot | 22.7 | 12.5 | 72.6 | 54.3 |
| Few-Shot (추론 없음) | 33.8 | 15.6 | 79.5 | 65.9 |
| Zero-Shot-CoT | 78.7 | 40.7 | 64.6 | 54.8 |
| Manual-CoT | 91.7 | 46.9 | 73.5 | 65.4 |
| Auto-CoT | 92.0 | 47.9 | 74.4 | 65.4 |

- **[논문]** 강점은 다단계 계산·논리처럼 중간 결론이 다음 단계의 입력이 되는 문제에서 나온다.
- **[논문, 주의]** 분류에 가까운 객관식 상식 문제(CSQA)에서는 Few-Shot이 Manual-CoT·Auto-CoT보다 높다(79.5 vs 73.5/74.4). Zero-Shot-CoT는 Zero-Shot보다 오히려 낮다(64.6 vs 72.6).
- **[추론]** "CoT면 분류도 좋아진다"는 결론은 이 논문에서 나오지 않는다. 자체 데이터로 검증이 필요하다.

## 2. 핵심 개념 3가지

### ① Misleading by Similarity: 비슷한 예시가 오히려 독이 된다
- 유사 질문 검색(Retrieval-Q-CoT)이 랜덤 샘플링(Random-Q-CoT)보다 못한 경우가 있었다. Zero-Shot-CoT 오답 128개 중 여전히 못 푼 비율은 46.9% 대 25.8%.
- 예: "남은 감자 조리 시간" 예시 3개가 모두 "the rest"를 "전체"로 잘못 해석했고, 테스트 문제도 같은 오류를 따라 했다.
- 구조: `유사 예시 검색 → 오류가 같은 군집에 몰림 → 오답 예시 동시 주입 → 오답 복제`

### ② 군집 기반 다양성 샘플링 (Auto-CoT의 핵심)
- 오류는 특정 군집에 몰려 있다(MultiArith의 한 군집 오류율 52.3%). 군집마다 1개씩 뽑으면 오답 예시가 섞여도 영향이 작다.
- 구조: `질문 전체 → SBERT 임베딩 → k-means(k=8) → 군집별 중심 최근접 질문 1개 → Zero-Shot-CoT로 추론 생성 → 휴리스틱 필터 → few-shot 프롬프트`
- 오답 예시가 50%까지 섞여도 Auto-CoT는 크게 안 떨어졌고, 같은 군집에서 뽑는 방식은 더 떨어졌다(Fig. 6).

### ③ 추론과 답의 일치성이 가장 중요하다
- 예시 속 질문을 섞으면 91.7 → 73.8, 추론이나 답을 섞으면 43.8 / 17.0으로 크게 떨어진다(Table 5).
- Table 6의 Wendy 사례는 추론이 "4+29−x=24"까지 갔는데 정답은 "29"다. 이런 예시는 근거 없이 답을 찍는 법을 가르친다.
- 답이 추론 안에 등장하는지 검사하는 필터로 잘못된 예시가 평균 1.3개에서 0.3개로 줄었다(Table 9, MultiArith).

## 3. 실무 적용: 영업 메모 → 광고주 상태 분류

**[추론]** 세 가지 원리를 옮기면 다음과 같다.
1. 예시는 군집별 대표 메모로 구성한다.
2. 추론과 라벨이 일치하는지 검증한다.
3. 추론은 짧고 구조화한다(5단계 이하).

### System Prompt Flow (예시)

```
[System]
당신은 광고 플랫폼의 광고주 케어 분석가입니다.
영업 메모를 읽고 광고주 상태를 분류하세요.

[상태 정의]
- 유지: 정상 집행, 특이 신호 없음
- 확장: 예산 증액·상품 추가 의사 표현
- 위험: 예산 축소·집행 중단 시사, 연락 회피, 경쟁사 언급
- 불만: 성과·정산·응대에 대한 명시적 불평

[추론 절차] 최대 5단계
1. 핵심 사실 추출: 메모에서 사실(발언·행동)만 인용
2. 신호 분류: 각 사실을 긍정/부정/중립 신호로 표시
3. 모호성 점검: 근거가 부족하거나 상충하면 "모호"로 표시하고 이유 기술
4. 기준 대입: 상태 정의와 대조해 후보 라벨 1~2개 도출
5. 최종 판단: 라벨 1개 + 확신도(높음/중간/낮음)

[출력: JSON]
{"reasoning": [...], "evidence_quotes": [...],
 "label": "...", "confidence": "...", "needs_review": true/false}

[Few-shot 예시 k개] 군집 대표 메모 + 검증 통과한 추론
```

### 모호한 메모 처리
- 메모: "이번 달 예산은 검토 중이라고 하심. 성과는 딱히 말씀 없음."
  1. 사실: 예산 검토 중, 성과 언급 없음
  2. 신호: 예산 검토(부정 가능성), 성과 무언급(중립)
  3. 모호: 감액 여부가 불명확하고 불만 표현도 없음
  4. 후보: 유지 vs 위험
  5. 위험, 확신도 낮음, `needs_review: true`
- 핵심은 "모호하면 억지로 고르지 말고 사람 검토로 넘긴다"는 탈출구(단계 3)다.

### 예시 구성 파이프라인 (Auto-CoT 적용)
1. 과거 메모 전체를 임베딩하고 k-means로 군집화한다(k는 라벨 수보다 넉넉히).
2. 군집 중심에 가까운 메모를 뽑는다.
3. 사람이 확정한 정답 라벨이 있다면 LLM 추론과 짝지어 검증한다. 논문에서도 어노테이션이 있으면 Retrieval-Q-CoT가 Manual-CoT를 넘었다.
4. 추론이 최종 라벨을 뒷받침하는지 규칙 또는 2차 호출로 확인한다.

## 4. DA·DX/AX 관점의 한계와 고려사항

토큰 비용, 지연시간, 환각 지표는 논문에 측정값이 없다. 아래는 논문의 설계 사실을 근거로 한 **[추론]**이며 실제 수치는 직접 측정해야 한다.

| 항목 | 논문에서 알 수 있는 것 | 실무 대응 |
|---|---|---|
| 토큰 비용 | 예시 k=4~8개에 각각 추론 체인이 붙어 입력이 길어진다. 예시는 5단계, 60토큰 이하로 제한했다. | 예시는 한 번만 구성해 프롬프트 접두부로 고정·캐싱한다. 추론 5단계 이하로 강제하고, 쉬운 메모는 CoT 없이 분기한다. |
| 지연시간 | 출력이 추론 문장만큼 길어진다(실험은 max_tokens=256). | 실시간이 아니면 배치 처리, `reasoning` 길이 상한을 둔다. |
| 환각 | Zero-Shot-CoT 오류율이 MultiArith에서 21.3%였고, 추론과 답이 어긋난 사례가 있었다. | 원문 인용(`evidence_quotes`)을 강제하고 메모 내 실제 존재 여부를 문자열 매칭으로 검증한다. 추론과 라벨이 어긋나면 `needs_review`. |
| 일관성 | 논문은 temperature=0 그리디 디코딩을 썼다. | temperature 0 유지. 위험 라벨처럼 중요한 건 다수결(self-consistency)을 쓰되 비용이 배로 늘어남을 감안한다. |
| 분포 변화 | 스트리밍 설정(Auto-CoT*)에서 2번째 배치부터 Manual-CoT 수준에 도달했다. | 새 메모가 계속 들어오므로 예시를 주기적으로 재군집화해 갱신한다. |

### 반드시 해야 할 검증
- CSQA처럼 분류형 과제에서 CoT가 Few-Shot보다 낮게 나왔으므로, 같은 라벨셋으로 **Few-Shot(추론 없음) vs Few-Shot-CoT A/B 비교**를 한다. 정확도가 비슷하면 더 싸고 빠른 쪽이 정답이다.
- 정확도만 보지 말고 이탈 케어가 목적이므로 **"위험" 클래스 재현율(recall)**과 오탐으로 인한 CS 부담을 함께 본다.
- 실험은 2022년 GPT-3(text-davinci-002)와 Codex 기준이다. 최신 모델은 CoT 없이도 잘하는 경우가 많아 절대 수치를 그대로 기대하면 안 된다.
- 영업 메모에는 고객사 정보가 있으므로 외부 API 전송 시 마스킹과 보안 정책 확인이 필요하다.

## 아티클 구성 제안
1. 도입: CoT 자동화가 왜 필요한가(수작업 예시의 28.2%p 편차)
2. 개념 ① → ② → ③ 순서로 실패 사례에서 해결책으로 전개
3. 영업 메모 분류 프롬프트 설계
4. "CoT가 항상 답은 아니다": 검증 결과(CSQA 사례와 본인 A/B 결과)
